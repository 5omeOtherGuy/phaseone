# ADR-0188: A re-attach with other MCP servers swaps the session's MCP generation

## Context

ADR-0182 lets an ACP client name MCP servers for its session and decided that "a load or resume that re-attaches to the open session keeps the servers it opened with": `p1 acp` decoded the `mcpServers` of such a request and dropped them. A client whose server list changed believed its new servers were connected, and the model never saw their tools, silently and on every re-attach. The owner reviewed #695's ASSUMPTION 4 on 2026-10-11 and ordered the fix (#800): on re-attach, compare the list with the session's; equal changes nothing; different builds a new generation from the environment's servers plus the new client list and swaps it whole (ADR-0181's generation swap, journalled); a failure refuses the load or resume with an error naming the server and keeps the old generation. The swap must keep ADR-0186's rule (an optional server that fails is skipped with its notice and record) and ADR-0184's scoping of client values. A re-attach is a request to the session process's loop, which talks to the host only through `SessionHandle`, so the swap needs a method on that contract.

## Decision

1. **Port.** `SessionHandle` gains `set_mcp_servers(servers, cancel)`: make `servers` the client's MCP servers of the session. It waits for a running turn, as `set_config` does; `cancel` stops it while it connects. The default refuses (`this session cannot change its MCP servers`), so every other session handle is unchanged.
2. **ACP adapter.** The session loop keeps the list the session was opened with. A `session/load` or `session/resume` that re-attaches with an equal list (the same entries in the same order, values included) is answered as before and calls nothing. A different list calls `set_mcp_servers` before the replay and the answer; on an error the request is answered `-32603` with `p1 could not change the session's MCP servers: <reason>`, and the session's list stays. The swap takes the agent, which a running prompt holds, so a re-attach with a different list that arrives during a prompt (or an inbox turn) waits for its end, and every open after it waits too; it goes before the prompts queued meanwhile. It releases a held prompt (D4), as the next prompt does, so it waits for the running turn and not for the background work that turn started. Once the client has left, such a re-attach is refused as the session having ended, as a prompt is.
3. **Host.** `run::swap_mcp_servers` compares the list with the one the session's generation was connected with (`McpServers::client`) and, when it differs, connects the environment's servers (from the environment the session started with) and the new list through the one connection path (`mcp::connect_all`, ADR-0181, ADR-0182, ADR-0186: the same name rules, an optional server that fails is skipped, everything else fails). It installs the result with the model the session runs now through the model switch's path (`install_switch`): the candidate is assembled with the new generation, `Agent::reconfigure` commits the new `Environment` record, and the assembly line names what the new generation skipped (`mcp_skipped`). The session adopts the new generation only once the agent installed it; on any failure before that nothing changes and the newly connected servers are dropped, which ends their processes. A journal that refuses the new assembly's line does so after the install, so that swap counts as applied and its error goes to stderr. The error is masked with every value the new list sends, as a start failure is (ADR-0184). Each skipped server's notice replaces the skip notices still waiting for the next turn (`mcp::PendingNotices`, the queue `mcp::skip_notices` empties right after a turn starts), so it is shown when the next turn starts, as a start's is, on the display-only notice path (the operator log, and a `notice` update for a client that takes them, ADR-0190): nothing may follow a `session/load` answer. A later model switch or module reload keeps the swapped generation.

## Consequences

An editor that changes its MCP servers and re-attaches gets the new servers' tools on the next turn, and the journal says when the tool set changed. A swap reconnects the environment's servers too: the generation is built whole, so their processes restart and their tools are listed again. A swap holds the agent and the session loop while it connects, bounded by the connection and listing timeouts per server: a `session/cancel` or a setting change sent meanwhile waits for it, and only the client leaving stops it. A re-attach during a prompt is answered only after that prompt's running turn. A swap's skip notices show at the next turn, not with the answer to the re-attach; the start's notices not yet shown are dropped with the generation they describe, whose assembly line keeps them. The ordering of a deferred re-attach before prompts that were already queued is a simplification: such prompts run with the new servers. The new generation starts its own numbering at 1; nothing reads the number outside tests. Since client servers are optional (ADR-0186, ADR-0190), a client server that does not connect or declares a tool it cannot expose does not refuse the re-attach: it is skipped with its notice, so the errors left are invalid or duplicate names, a name the environment uses, a tool-name clash, a required environment server that no longer connects or exposes its tools, and a cancelled swap. The router forwards a re-attach to the session's process unchanged, so `p1 acp`'s router needed no change. The TCK's load and resume tests send the list the session opened with and see no change.

## Alternatives considered

Keeping the environment's live connections and reconnecting only the client's servers: fewer restarts, but a generation would no longer be built whole from one connection pass, and `ToolGenerations` would need a constructor that mixes kept and new connections. Answering a re-attach at once and applying the swap at the next boundary, as a setting change during a prompt is: the request could no longer fail with the reason. Refusing a re-attach that changes the servers during a prompt: a client would have to retry with no way to know when. Comparing the lists in the host only: every re-attach would wait for the agent lock, including the TCK's equal-list ones during a prompt.

## Evidence

`cargo test -p p1-acp --test mcp_servers` (`a_reattach_swaps_the_servers_only_when_its_list_differs`: an equal list calls nothing, a different one is swapped before the answer, a failing swap is `-32603` with the reason and keeps the list; `a_reattach_that_swaps_waits_for_the_running_prompt`: the load is answered after the prompt and swapped only then; a negative control that drops the wait fails it); `cargo test -p p1-host --test acp_mcp_servers` (`a_reattach_with_another_list_swaps_the_generation_journalled`: a bash stdio server named in `session/new`, an equal-list `session/load` starts no server, a `session/resume` naming another server and a nonexistent command swaps the generation: the next turn declares only the new tool, its client value is masked, a second `Environment` record names `mcp:two` and not `mcp:sh`, the last assembly line records `gone` as skipped, and its notice reaches a client that takes notices as one `notice` update after the resume's answer and before the next prompt's; `a_reattach_whose_swap_fails_is_refused_and_keeps_the_generation`: a client server named like the environment's is `-32603` naming `sh` before any server starts, and a required environment server that no longer starts is `-32603` naming `sh` after its one retry, neither error nor the journal holding the value, the environment's server answers the next turn, one `Environment` record; a negative control that makes the host swap a no-op fails both).
